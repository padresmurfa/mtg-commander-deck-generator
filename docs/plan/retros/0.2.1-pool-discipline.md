### Not delivered

Nothing from the sprint scope. Two things worth stating anyway:

- **Per-pool arena capacities.** One `arena_bytes` sizes every pooled arena, heap or stack, and a
  frame arena is nothing like an evaluation arena. Deliberate: two capacities would need the fatal
  report to name *which arena*, which is a table mapping worker names to config keys, and that
  table rots. Revisit when a real evaluation makes the difference visible. Until then the record
  reports `heap_arena_peak` and `stack_arena_peak` separately, so the evidence is being collected.
- **The stack pool has exactly one caller.** `mfsim validate` nests three frames and unwinds them,
  which is enough to prove the discipline works and not enough to prove it is the right shape.
  There are no call frames to model until there is a simulation.

### The pool was the one place the design argued against itself

Sprint 0.2 spent its whole length removing recoverable environmental failure — no NULL checks, no
half-arena to salvage, a process that dies and an orchestrator that fixes the number. And then the
pool it built ran dry, quietly made another arena, and incremented a counter nobody read.

That is the rejected shape exactly: a recoverable failure, an unbounded footprint, and a signal
with no consumer. It survived review in 0.2 because it looked like a cache-miss counter, which is a
normal thing for a pool to have. The tell was that nothing was *sized* by it.

It now behaves like everything else here: a fixed depth, a fatal, a report, and an orchestrator
that grows the number and relaunches. The smoke test drives a run from `stack_pool_depth: 1` up to
4 across relaunches and watches it persist — the same evidence the arena story has.

### Two corrections to things 0.2 asserted

Both were comments that had never been checked against the machine:

- **`alignof(max_align_t)` is 8 here, not 16.** `arena.h` said the grain *was* `alignof(max_align_t)`
  "on arm64". A probe says otherwise: `long double` is 8 bytes on Darwin arm64, so `max_align_t` is
  8, while `__int128` needs 16 and `malloc` gives 16. The grain stays 16 and the reasoning is now
  the honest one — `max_align_t` covers the *fundamental* types, and everything this code will
  actually put in an arena is an extended type it says nothing about. Three `_Static_assert`s prove
  the choice rather than describing it, so a port that disagrees fails to compile.
- **The alignment contract was documented but not enforced.** `mf_arena_alloc_aligned`'s header said
  `align` must be a power of two no larger than a cache line. Nothing checked. `align == 0` would
  have been diagnosed as an *arena too small* — sending the orchestrator off to grow memory over a
  caller's bug — and `align == 256` would have returned an address that was not 256-aligned, with
  no complaint from anybody. Both are wrong answers rather than slow ones, and both are now exit 72.

## What the coverage floor bought this time

Less than 0.2, and that is the interesting part. No defect was found by a failing test this sprint;
what the floor found was **dead weight and untestable design**:

- **`mf_arena_array`'s `count != 0` guard went uncovered** the moment the pool stopped asking for a
  zero-length array. Exactly the pattern 0.2's retro warned about — a branch a refactor has just
  made dead — and it took one re-read of the branch report to catch, not a sprint. The guard is
  load-bearing (it stands in front of a division), so it gained a test rather than being deleted.
- **A `max()` of two pool high-water marks could not be covered both ways.** Frames are 4 KiB and
  work items are 1 MiB, so the stack side never wins, and contriving a run where it did would have
  been a test written to serve a branch. Reporting both peaks separately removes the branch *and*
  says which pool wanted the room — which is the more useful record anyway. Untestable code is a
  design defect here, and this is what that rule looks like when it pays.

Mutation testing did the work the floor did not: 16 mutations across `panic`, `pool` and `orch`,
all killed. Two are worth recording.

- A mutation that dropped the `>` from the live-water-mark comparison **survived**, because the mark
  is only ever written while it is rising — the conditional and the unconditional assignment are
  indistinguishable until something borrows *less* than the peak after the peak has passed. The test
  now re-acquires after releasing. This is the class of bug a coverage number cannot see: the branch
  was covered, the assertion was not strong enough.
- A mutation that dropped the swap in `mf_pool_release` was killed by the *implementation's own*
  invariant check rather than by an assertion — the duplicate arena was caught at the next release.
  A legitimate kill, and a small piece of evidence that the identity check is doing real work.

## Revised risks

| Risk | Change |
| ---- | ------ |
| **`_FORTIFY_SOURCE` folded branches cap coverage** | ↔ Unchanged in kind, slightly larger. **23 of the 24 residual branches are folded**, up from 18 — the new `fprintf`/`snprintf` calls in `orch` and `panic` each bring one. The 24th is still `if (g_hook)` in `mf_panic`, the actual `_exit`, covered by `smoke.sh` with real exit codes 70, 73 and 2 |
| **Pre-optimising the memory layer** | ↑ Slightly worse, and worth saying so. 0.2 built a shape for a fast implementation that does not exist. 0.2.1 built a *second* shape — the stack pool — with one caller and no simulation to judge it against. The heap pool at least has a use; the stack pool is a bet that call-frame arenas are a thing this simulator will want. Mitigated only by how little code it is: the two kinds differ by one comparison |
| **Eager pool stocking multiplies the footprint** | ⚠️ New. `depth × arena_bytes` per pool is reserved before a run does anything, and there are two pools. At 0.2's 64 MiB default that would have been 384 MiB at rest for a `validate` that uses 1 MiB. Handled by dropping the default to 8 MiB, which is as much a guess as 64 was — it just does not reserve most of a gigabyte to find out |
| **Arena sizing is a guess that has to be right** | ↓ Further retired: the same loop now covers depths. Two independent knobs converge, not one |
| **Two processes is more machinery than one** | ↔ Unchanged. It bought a second self-correcting parameter for no new machinery at all — the growth planner gained a branch and a struct field |
| **Coverage floor unreachable in C** | ↔ Line 100%, function 100%, branch 97.00% (was 97.16%). The dip is entirely the extra folded branches; the count of *real* uncovered branches is still one |
