## Design amendments

Four, all applied in the same change as this retro.

| Document | Change | Why |
| -------- | ------ | --- |
| `simulator-spec.yaml` → `parameters.dependencies` | Recorded that the JSON parser/writer and the test harness are **written in-tree**, not vendored | The plan said "vendored single-header parser". Vendoring means fetching a dependency this project has no way to audit, and both turned out to be ~300 and ~60 lines. Code we own is code the coverage floor can hold |
| `simulator-spec.yaml` → new `invariants.testable_failure_paths` | Added the allocation seam as an architectural rule | Emerged from the coverage floor, below |
| `simulator-spec.yaml` → `schemas.card_struct` unaffected; `target_host.compile_flags` gains `-Wshadow -Wconversion -Wsign-conversion` | Stricter warnings than the spec listed | They caught a real sign-conversion defect in a test on the first build. Cheap to keep, expensive to add later |
| `simulator-design.md` §17.1 | Noted that JSON number output uses **shortest round-trip**, not `%.17g` | `%.17g` renders 0.1 as `0.10000000000000001`. Determinism requires exact round-trip, not maximum precision — so try `%.15g`, `%.16g`, `%.17g` and take the first that reparses identically |

### The allocation seam is the interesting one

Branch coverage stalled at **84%**, and the gap was almost entirely `if (!ptr) return MF_ERR_INTERNAL;`
— out-of-memory paths no test could reach. `CLAUDE.md` §1 says not to keep unreachable defensive
branches, which left two options: delete the OOM handling, or make it reachable.

Deleting it is wrong for a tool meant to run unattended for hours. So `mf/alloc.h` was added: every
allocation goes through it, and tests can fail the *n*th allocation on demand.

That enabled an **OOM sweep** — run an operation once to count its allocations, then run it again
failing each one in turn. It found no defects, but it is now a standing property test: any future
allocation failure path is covered the moment it is written. Branch coverage went 84% → 92% from
this alone.

The coverage floor did not just measure the design here; it changed it, for the better. Worth
remembering when the floor next feels like an obstacle.

### Two branches were deleted rather than tested

- `parse_string_raw`'s NUL check inside the copy loop: the pre-scan already proves a closing quote
  exists, so it was genuinely dead.
- `mf_config_load_file`'s `fseek`/`ftell` error handling: replaced with incremental reads. That
  removed two untestable branches **and** made `--config /dev/stdin` work, which seek-to-end never
  could.

## Revised risks

| Risk | Change |
| ---- | ------ |
| **Coverage floor unreachable in C** | ↓ Reduced. 100% line / 97% branch on the first module set, with the residual being macOS `_FORTIFY_SOURCE` folded branches (see below) |
| **`_FORTIFY_SOURCE` folded branches cap achievable coverage** | ⚠️ New. macOS expands `snprintf` into `__snprintf_chk`, whose internal branches llvm-cov reports as `Folded` and counts against us. ~8 of the 15 residual branches are this. It is a measurement artifact, not untested code, and it puts a practical ceiling somewhere below 100%. The 95% floor has ample headroom; do not chase 100% |
| **Sanitizer noise** | ⚠️ New but handled. LeakSanitizer reports ~1 KB "leaked" through Apple's `snprintf` float conversion. Confirmed from the stacks (frames #0–#8 are libsystem). Suppressed in `tests/lsan.supp`, scoped to system libraries only — nothing in `src/` is suppressed |
| **TDD slows early work** | ↓ Reduced. The suite caught the sign-conversion bug, an over-tolerant artifact test, and drove two genuine design improvements. It did not feel like a tax |
